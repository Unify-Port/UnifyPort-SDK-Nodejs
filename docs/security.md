# Security Boundaries

[English](security.md) | [简体中文](zh-CN/security.md)

## Threat Model

This project protects against the following risks:

- API keys, account authorization passwords, verification codes, session payloads, or one-time secrets entering source code, logs, or model context;
- credentials being sent to the wrong origin or forwarded unintentionally across a redirect;
- automatic retry repeating an operation with side effects;
- oversized or malicious responses contaminating logs, error objects, or MCP context;
- JavaScript precision loss causing an operation to target the wrong resource;
- a generic MCP tool bypassing the operation allowlist or permission switches;
- incomplete webhook signature rules creating a false security guarantee.

## Authentication Scope Isolation

- Device API credentials are never forwarded across origins or redirects.
- `X-Api-Key` can only come from `DeviceClientConfig` or the MCP startup environment.
- Per-operation `headers` and tool input cannot override authentication fields.
- The base URL is validated when the client is created. HTTPS is required by default; HTTP can be enabled explicitly for loopback development only.
- The SDK does not automatically follow a redirect that could carry an authentication header to another origin.

Account authorization operations under the Device API's `/v1/accounts/...` paths can accept a password, verification code, or session payload and can return a temporary authorization secret. These are provider account resources, not a separate authentication service, but the same credential isolation rules still apply.

## Credential Lifecycle

### Device API

The API key remains only in the client closure or request header. It never appears in a public configuration dump, error detail, retry log, or MCP result. One-time plaintext returned by a create or rotate operation is delivered only to the direct SDK caller.

## Log and Error Redaction

A public error may retain:

- the HTTP status;
- a server error `code` after character allowlisting and length limiting;
- a request ID after character allowlisting and length limiting;
- a stable, generic message generated by the SDK.

Never record:

- `Authorization` or `X-Api-Key`;
- passwords, verification codes, session payloads, or webhook signing secrets;
- one-time plaintext returned by API key creation or rotation;
- a complete request/response body or client configuration;
- an upstream raw message, details object, complete URL query, or raw cause;
- a raw `Response`, response headers, or another transport object that can bypass field-level redaction.

Reading a non-JSON error body is size-limited and produces a generic error message. If error parsing fails, it must not fall back to printing the raw body. A successful result may retain the `Response` explicitly required by the caller, but public error classes store only filtered status, code, and request ID values so that loggers and serializers cannot expand an exception into headers or a body.

Response limits apply to both the wire body and integer-normalized JSON. A short token written in scientific notation can expand substantially during normalization. If normalization would exceed `maxResponseBytes`, processing fails immediately with a stable error instead of constructing the complete expanded string.

## Timeout, Cancellation, and Retry

Every request has a finite timeout and supports the caller's `AbortSignal`. Signal composition cleans up timers and listeners when the request ends.

Automatic retry uses an explicit allowlist:

- it applies only to safe operations marked `retryable` by policy;
- it handles connection failures and temporary statuses such as `408`, `429`, `502`, `503`, and `504`;
- it honors a valid, capped `Retry-After`;
- otherwise it uses full jitter with limits on attempts and total wait time;
- after caller abort, it stops immediately without sleeping or sending another request.

Normal writes, one-time-secret operations, and account authorization steps are not retried by default. If a future public protocol provides an idempotency key, retry can be enabled for an individual operation only after the contract and tests cover that guarantee explicitly.

## Least-Privilege MCP Exposure

MCP exposure is not a mirror of SDK coverage. The SDK can support direct application calls while MCP further limits the surface visible to a model:

| Classification | Default | Writes enabled | Writes and destructive enabled |
| -------------- | ------- | -------------- | ------------------------------ |
| read           | Visible | Visible        | Visible                        |
| write          | Hidden  | Visible        | Visible                        |
| destructive    | Hidden  | Hidden         | Visible                        |
| never          | Hidden  | Hidden         | Hidden                         |

The following operations are always classified as `never`:

- account authorization flows that require human interaction or return a temporary secret;
- operations that accept a password, verification code, session payload, or signing secret;
- operations that return a one-time API key, invite code, or equivalent secret;
- operations whose side effects, data exposure, or retry boundaries cannot be established.

MCP never provides a generic tool with an arbitrary base URL, header, method, or path. Tool input is validated against the corresponding OpenAPI JSON Schema and rejects extra authentication fields. Tool results also filter sensitive fields and cap error body size.

In stdio mode, normal logs written to `stdout` would corrupt JSON-RPC frames. The implementation writes logs to `stderr` and redacts them before output. It does not print complete configuration, request headers, response bodies, or caught error objects.

## JavaScript `uint64` and Data Integrity

Parsing an ID larger than `Number.MAX_SAFE_INTEGER` as a `number` silently changes its value and can make a later operation target the wrong account, API key, or resource. This is a security and integrity issue, not a type preference. A `uint64` without an explicit safe range in the public contract remains a string. Boundary tests cover at least `9007199254740991` and a larger valid value.

## Webhook Boundary

The SDK provides a verification helper only after an approved public API schema and release notes fully define the signature version, canonical payload, time tolerance, and replay rules. Guessing an algorithm before the protocol is complete would give callers a false security guarantee.

## Dependencies and Releases

- Dependencies are pinned with the lockfile. An upgrade reviews the changelog, Node engine, ESM/CJS exports, and transitive diff.
- `pnpm package:check` validates tarball contents, exports, and declaration files. Development fixtures and local credentials never enter a package.
- A new `@unifyport/sdk-node` version is published only after its license, version, registry settings, and complete quality gates have been reviewed. `@unifyport/mcp-server` remains `private: true` so an SDK release does not expand MCP distribution.
- Every public delivery runs `pnpm public:check` to confirm that documentation, configuration, and artifacts remain within the public boundary.

## Security Review Checklist

For every new or changed operation, answer at least these questions:

1. Can its authentication cross an origin boundary?
2. Does it change server or browser state, and can retry be proven safe after a failure?
3. Does its request or response contain a secret, personal data, or a large payload?
4. Can an ID or cursor exceed JavaScript's safe integer range?
5. Is its MCP classification `read`, `write`, `destructive`, or `never`?
6. Does it introduce a redirect, webhook replay, or SSRF boundary?
7. Which automated checks prove these classifications instead of covering only the happy path?
